TechHaven 上线就绪度评估

评估日期：2026-09-04 · 评估范围：前端 SPA、Agent Gateway、Agent DB、techhaven-mcp、部署脚本、CI/CD · 依据：代码与文档实证（非计划书）

总体结论：当前不具备多用户正式上线条件，但底座质量显著高于同类自研项目。
按项目自己的成熟度定义（ROADMAP §1），各核心能力普遍处于 verified-mock，距 production 门禁还差身份链路、真实引擎验证、观测性三块硬骨头。建议以「单组织受限试点」为第一个上线目标，而非直接开放。

一、分维度评估

1. 部署工程 —— B（试点可上）

项现状评价
发布脚本npm run deploy:server 一条命令：构建→打包→SCP→远端解压→原子切软链接→健康检查→失败自动回滚→保留 5 版优秀 脚本有路径注入防护、tar 条目安全校验
CI/CD4 个 workflow：前端 build+test+体积预算、mcp/bridge/gateway 各自 typecheck+test+smoke良好
进程管理Gateway 有 systemd 安装脚本 + 无 root 兜底脚本（带 /proc cmdline 校验防误杀）良好
Nginx有示例配置（SPA 回退/SSE/鉴权注入），但只是示例，未经真实域名验证待演练
数据库部署迁移脚本成熟（按序幂等执行），但生产 PG 实例不存在、无备份策略、无定时清理任务硬缺口
监控告警无。仅 JSONL + stderr，无 metrics/错误上报/告警通道硬缺口

2. 安全 —— C+（有硬缺口）

项现状评价
用户身份链路Gateway 要求 BFF 注入 X-TechHaven-Actor；Nginx 示例用 auth_request 指向 BFF——但 BFF 服务不存在。生产链路中 actor 注入只存在于 vite 开发代理（写死 user:1）P0 阻塞 多用户下要么全员 401，要么全员共享一个身份
密钥存储AI Key AES-256-GCM 密文入库（含版本头/指纹/脱敏串），主密钥环境变量注入、支持轮换；明文只在解析瞬间存在于内存；有测试断言"明文不出现在任何 HTTP 响应"优秀 但主密钥无 KMS，备份流程未成文
多租户隔离API 层 org 隔离有测试覆盖；但 dsh 子进程与 Gateway 同机同用户运行，无容器/沙箱，网络出站不受限P0（多组织前）
前端安全Mermaid strict 模式、9 项凭据脱敏回归（反向验证过）、密钥输入有形态校验良好
传输安全Nginx 示例是 80 端口明文；AI Key 校验强制 HTTPS 上游但前端到网关链路需 TLS试点前必须配 TLS
限流Gateway 有组织级会话配额（冒烟验证）；Nginx 层无 IP 限流、无 AI 配额的请求级限制待补

3. 产品功能 —— B-（博客域可上线，Agent 域是半成品）

  • 博客/组织/研发/后台域：页面、service、真实后端（techhaven.website）都在运行，属于已上线部分。
  • Agent 会话/审批/SSE：mock 驱动下 41 项冒烟全绿，前端面板实测通过——但全部跑在 mock 上。
  • dsh 真实引擎：implemented 但 SDK 是 0.1.1-rc.2 预发布版，无一次 live 验证（无权限应答、无单 turn cancel 验证）。这是产品核心卖点，恰恰是最没验证的部分。
  • AI 配置资产（本次新增）：后端与 Gateway 全链路就绪（100/100 测试），但前端 UI 未接入，用户仍走旧的单套配置接口。
  • 组织配置管理：数据模型有、HTTP 不开放（有意的安全取舍）、管理界面不存在——组织管理员目前只能直插数据库。

4. 数据层 —— B-

  • Schema 设计成熟：枚举约束、部分唯一索引（默认配置互斥）、微元计价、审计明细与聚合分离、保留策略成文。
  • 迁移机制按序幂等，可重复执行。
  • 缺口：无生产 PG 实例证据（live smoke 存在但未跑过真实环境）；agent_events 量大需按月分区（已标注未实施）；user→org 归属在产品后端，Agent DB 只有 ID 引用，两库之间无一致性保障；备份/恢复从未演练。

5. 工程质量 —— A-（本项目最强项）

  • 测试密度：Gateway 100+、MCP 32、Bridge 14+4、前端 22 项，另有真实 HTTP/SSE 重连回归；关键安全行为（脱敏、越权、明文不外泄）都有断言。
  • 文档文化突出：RFC、ROADMAP（严格状态定义，明文禁止把 implemented 写成"完成上线"）、每个服务有 README 与 env 模板。
  • 体积预算制：主入口 gzip 93.3KB（预算 256KB），CI 卡口。
  • 扣分项：无 ESLint（仅 Prettier）、42 个未提交变更（含全部部署脚本与 AI 资产）——变更管理与 CI 门禁脱节；TypeScript 严格度未系统审计。

6. 可靠性 —— C+

  • 发布回滚机制好（20 秒健康检查失败自动回退+日志输出），但从未在真实服务器演练。
  • 单实例架构：JSONL spool、内存会话注册表，重启靠事件回放——设计自洽，但决定了不能水平扩展，重启窗口内会话不可用。
  • SSE 断线重连、背压断开慢客户端、幂等提案都有覆盖。
  • 无 SLO、无容量模型、无故障演练记录。

二、上线阻塞清单

P0 不解决无法多用户上线

P1 试点开放前应完成

  • 前端接入多套 AI 配置 UI（后端已就绪）；组织配置管理最小工具（哪怕是 CLI）。
  • 主密钥备份/轮换 runbook 成文并演练一次。
  • Nginx IP 限流 + index.html 禁缓存验证。
  • 回滚演练：在测试服务器完整走一次"发布→健康检查失败→自动回滚"。
  • 产品后端与 Agent DB 的组织归属一致性核对脚本。

P2 正式多组织开放前（ROADMAP R4）

  • dsh 子进程容器化/沙箱化 + 网络出站 allowlist；
  • SLO 与告警体系、容量与成本看板；
  • ASVS 检查、威胁建模、SBOM、密钥全面轮换；
  • 负载/长稳/恢复演练、组织级 kill switch；
  • 多实例化（去 JSONL 单实例假设）。

三、做得好的（应保持）

  • 诚实的状态管理：ROADMAP 明文禁止把 implemented 写成"完成上线"，本次评估与它的自评高度一致——这种自知之明在自研项目里罕见。
  • 安全默认值：Gateway 默认只监听回环、工具默认关闭逐项 opt-in、写操作默认走审批、密钥默认加密+脱敏+审计。
  • 失败关闭（fail-closed）：配置缺失拒绝启动而非带病运行；提案未决自动过期=默认拒绝。
  • 发布工程：原子软链接切换+健康检查+自动回滚，好于很多手写 rsync 的团队。

四、建议路径

第 1 步（本周）：提交全部变更 → 生产 PG + TLS + 最小告警 → 测试服务器完整演练发布/回滚。
第 2 步（1–2 周）：实现 BFF 补齐身份链路；dsh SDK 稳定后在测试环境跑通第一条真实 Agent 会话。
第 3 步（第 3–4 周）：前端接入多套配置；单组织 3–5 人灰度试点（ROADMAP R3），配额从紧、观测盯紧。
不做的事：跳过试点直接开放多组织；在 dsh 未验证前宣传 Agent 能力。

评分刻度：A 可直接上线 / B 试点可上 / C 存在硬缺口 / D 不可用。本报告基于静态代码审查、CI 配置、测试套件与既有文档，未包含渗透测试与负载测试。
